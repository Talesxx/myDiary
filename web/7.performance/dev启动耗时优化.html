dev 启动耗时优化 ​

依赖安装从 40 多秒降到 1 秒左右，dev server 启动从 23 秒降到 0.3 秒（真机数据），沙盒里整条链最终 4~5 秒。

记录一下怎么测的、怎么定位的、怎么取舍的。

背景 ​

页面再沙盒内快速启动，改完马上看到效果。开发者从进沙盒到看见页面这一段是整条体验的门槛，目标是 10 秒以内。

由三部分组成：

  • 依赖安装
  • dev server 启动
  • 浏览器打开页面到可见

有个测量上的前提要说清楚。真机和沙盒速度不一样，沙盒大约慢一倍。文中的 dev 启动数据都是真机上测的，而 10 秒目标指的是沙盒里整条链的耗时——三段之和。所以判断"还差多少"的时候，要把三段都折算到沙盒再加起来看。"慢一倍"这个系数不是通用的，只对 IO / CPU 密集的操作成立，详细说明放在文末。

依赖安装 ​

一开始测下来是 40 多秒，占了启动预算的大头。

翻 package.json，找到一条 create-react-app 时期留下的 react-scripts 等无用依赖。这个项目其实只用了 webpack，react-scripts 是当初试 create-app 时装的，后来没启用，但一直没删——上一轮优化的时候漏掉了。它自己会拉进来上千个传递依赖，所以哪怕代码里完全没用到，每次安装还是要完整下载一遍。

删掉它们，降到 20 秒左右。

再往下压就得解决"每次都要重新下载安装依赖"。沙盒里把上一次启动装好的东西留下来复用：

  • node_modules 本身保留
  • npm 的下载缓存（~/.npm）保留

这样下次启动 npm 就不用重新下载，只需要走一遍检查和增量。

优化结果是真机 1 秒左右，沙盒 2~3 秒。

转译器替换 ​

dev 启动大概 20 秒（真机 23478ms）。

项目用 webpack，转译走 babel-loader。Babel 是纯 JS 实现的，依赖树一大，转译就吃掉 dev 启动的大部分时间。

webpack 不动，只把 babel-loader 换掉，两种方案都测了：

方案dev 启动相对基线
babel-loader（基线）23478ms—
swc-loader7096ms−70%
esbuild-loader6038ms−74%

esbuild 是 Go 写的，swc 是 Rust 写的，都是原生二进制，把 Babel 那条逐文件解析转换的 JS 流程整个替掉了，收益主要来自这里。

两者之间 esbuild 在本项目快一点，大概 15%。在沙盒里复测时差距更大、esbuild 优势更明显，但当时没记数据，所以只能说在这个项目上 esbuild 更快，不好推广成普遍结论。

没保留 Babel 兜底，原因有两个：一是项目里没用到 esbuild 不支持的东西（装饰器、自定义 babel-plugin、babel-plugin-import 这类按需引入等）；二是这是个后台管理项目，不用兼容老浏览器，所以 @babel/preset-env 的 targets 降级和 core-js 注入都不需要了。Babel 在这条链上的活儿等于全没了。

这两条是前提。如果项目要兼容老浏览器，或者重度依赖 Babel 插件生态，就不能这么直接换。

换完暴露出一批写法问题——这些代码之前就是有问题的，只是 Babel 一直替它们兜着。实际碰到的有两类。

一类是在声明之前使用变量。let / const 有暂时性死区，声明前访问会报错。但 Babel 转成 ES5 之后 let / const 变成了 var，死区就没了，这类代码在 Babel 下一直静默通过。esbuild 保留了原语义，于是直接报 Cannot access 'x' before initialization。

这类代码本来就是错的，Babel 只是把错误推到了运行时，甚至因为退化成 var 而永远不会暴露。换 esbuild 等于把一个潜伏很久的问题翻出来了。

另一类是 TypeScript 的类型当值用。esbuild 逐个文件转译（相当于开了 isolatedModules），看不到跨文件的信息，所以：

  • import { SomeType } 没加 type 关键字的话，类型在运行时并不存在，esbuild 判断不出这是类型还是值，会报"没有这个导出"。得写成 import type { SomeType } 或者 import { type SomeType }
  • export { SomeInterface } 这种类型当值导出也一样会失败

最后 dev 启动从 23478ms 到 6038ms，降了约 74%。 在沙盒中启动需要12470ms 仍然严重超标

编译模型选型 （切换思路） ​

换完 esbuild-loader，真机是 6038ms，沙盒 12s，三段加起来 16~17s，还是没进 10 秒。于是思路从"换 loader"变成"换编译模型"，看了两个方案：

  • webpack 的 lazyCompilation：配置不动，把模块编译推迟到真正被请求的时候
  • Vite：开发期不打包，转成原生 ESM 交给浏览器按需请求，服务端只做单个模块的即时转换

两个方案都有个前提：得配合懒加载（动态 import()）。启动时只编译当前路由，其余等访问到再说。没有懒路由的话，两者都退化成启动时全量编译，Vite还有收益，lazyCompilation收益基本没了。

lazyCompilation：启动快了，切页面慢 ​

这是 webpack 的实验性特性。问题是切换路由很慢，用户点下去要等 2~3 秒页面才切，大页面尤其明显。

原因跟运行环境有关：

  1. 这套东西跑在沙盒上，链路是 浏览器 → 沙盒 → 编译 → 回显，中间有一次远程往返
  2. lazyCompilation 把一个路由需要的模块当成一个 chunk 整体构建，构建完之前没有东西可以返回
  3. 于是"构建一个大 chunk"的时间加上远程往返，整个落在了用户点击这条路径上

启动确实变快了，但成本只是从启动挪到了页面且换和用户操作。 这是不可接受的

Vite：启动毫秒级 ​

Vite 不做整包构建，服务端每次只转换一个模块，响应快而且可以并行，上面那种点击后等两三秒的情况没有出现。

真机实测的 dev server 启动：

方案启动后续表现
webpack + esbuild-loader（对照）6038ms启动时全量编译完
webpack + esbuild-loader + lazyCompilation2096ms切路由时约 2 秒的长构建
Vite263ms无此问题

一路下来是 23478ms → 6038ms → 2096ms → 263ms。

为什么 Vite 在沙盒这种远程弱算力的环境里反而占优？沙盒还是要为每个模块做转换，Vite 没有把活挪出沙盒，区别在粒度：

  • lazyCompilation：一个路由 = 一个 chunk，要等这个 chunk 里所有模块都构建完才返回，单次响应慢而且是阻塞的
  • Vite：一个模块 = 一次独立的转换，毫秒级返回，多个模块的请求可以并行，不存在"等一整块"的时刻

Vite 不是省掉了远程往返，而是把一次长往返拆成了一串短往返，浏览器拿到一小片就能开始渲染。

结论 ​

最后从 webpack 迁到了 Vite。

要说明的是，做这个决定不是因为 263ms 这个数字。单看启动耗时，lazyCompilation 已经压到 2096ms 了。真正决定的是成本放在哪：

lazyCompilationVite
启动2096ms263ms
点击路由后等 2 秒毫秒级

在沙盒这种远程环境里，把等待放到用户操作之后，体感代价比放在启动阶段大得多。

结果 ​

沙盒里三段：

阶段耗时
依赖安装2~3s
项目启动200~300ms
打开页面 → 可见~2s(内)
合计4~5s

10 秒的目标达到了，余量还比较足。同样三段在真机上，依赖安装约 1s，另外两段跟沙盒差不多。

关于 263ms 这个数字要单独说一下。它跟前面那些不是一回事：23478 / 7096 / 6038 / 2096 都是 webpack 编译完成的时间，这一刻所有模块（或该 chunk 的模块）已经编译好、可以直接服务了；263ms 是 Vite 的 ready in，只是服务器起来了，一个模块都还没编译。

Vite 没有把编译消灭掉，只是把它从启动阶段挪到了浏览器请求的时候，按模块粒度摊开。真正公平的口径是"到页面可见"的端到端时间，就是上面那张表。

一条教训：启动耗时是端到端指标 ​

这次最有用的经验跟构建配置没关系。

链路上同时有两个独立问题，量级差了大概 20 倍。只修掉容易发现的那个，启动耗时还是达不到目标——慢是会叠加的，修掉小的那个不会让大的消失。

具体来说，排查时一度把方向锁定在构建链上（loader、编译模型），也确实拿到了 23478ms → 6038ms 的收益。但真正吃时间的还有一层，而且量级更大，详见下面那节。

两个可以复用的做法：

  1. 先把链路每一段的耗时量出来，再动手。不然容易把精力花在只占 10% 的地方，真正的大头在别处。
  2. 区分"工具报出来的错"和"真正影响用户的慢"。这次排查里出现过大量 DNS 报错，后来确认是测试工具自己的解析器有问题，是个假线索，跟性能无关。

特殊一节：请求代理（stagewise） ​

链路上接了一个叫 stagewise 的代理层，作用是让用户在页面上直接点选元素、把信息传给 agent，是"AI 改页面"这套交互的基础设施。所有页面请求都经过它。

现象是浏览器访问 dev 链接时，大的 JS 文件响应异常：

请求响应时间
某大文件19.74s
某大文件16.82s

正常情况下应该是毫秒到百毫秒级。这个量级已经远超构建链的开销——前面所有构建优化省下来的时间，可能还不够给一个文件赔的。

原因是 stagewise 转发响应时不是流式的。它先把整个文件读下来放进内存，再往外发。小文件感觉不到差别，大文件就得等整个下完才能开始转发，中间还多了一层内存处理。文件越大越明显，所以十六七秒这种量级只出现在大文件上。

这个方向一开始没找到。链路上有这么个代理，但排查时并不知道，直觉判断是网络问题——远程环境加大文件，第一反应就是网络。

那段时间确实也发现沙盒侧有个独立的问题：网络抖动时访问会被拉长，平台方承认并已上报处理。但它只有秒级量级，实测大约 2.5% 的请求出现 250ms 到 7.2s 的尖刺，解释不了 16~20s。两者差了整整一个数量级，正因为对不上，才继续往链路上找，最后定位到 stagewise。

这两个问题互相独立。只修掉更容易发现的网络抖动，启动耗时依然不达标。

改法是把 stagewise 的职责范围收窄：

  • HTML 文件：注入（stagewise 要在页面里注入自己的脚本，这是它存在的理由）
  • 其他所有文件：直接隧道转发，不解析、不缓冲、不重写，等价于只做一层端口转发（3000 → 3100）

改完之后：

文件类型优化前优化后
HTML（需注入）—几十 ms ~ 100ms
其他文件19.74s / 16.82s3 ~ 6ms

关于「沙盒比真机慢一倍」 ​

那个 2× 来自算力和磁盘吞吐的差距，所以只对 IO / CPU 密集的操作成立。webpack 的启动正好是"启动即全量构建"，属于这一类——真机那 23478ms 是构建慢，不是启动慢。

到了无打包模式，启动阶段几乎不干计算，只有进程启动和少量磁盘 IO：

操作类型沙盒 vs 真机例子
IO / CPU 密集型约 2×依赖安装（真机~1s → 沙盒 2~3s）、webpack 全量构建（真机 23478ms → 沙盒 ~47s）
几乎不干活的启动差距很小Viteready（真机 263ms → 沙盒 200~300ms）

所以更准确的说法是：沙盒慢在算力和磁盘吞吐上，不占用这两样的操作就不会被拖慢。

这也是无打包方案在这个场景真正的价值——它抹掉的是"沙盒比真机慢一倍"这个劣势本身，因为这个劣势来自 CPU 和磁盘的密集占用，而无打包方案恰好不占用。同样也解释了为什么 lazyCompilation 在沙盒里特别难受：它把密集占用挪到了用户交互路径上，正好撞在沙盒最弱的地方。

附录：平台侧网络抖动排查 ​

这是前面提到的"另一个独立问题"的排查记录。它是平台侧的问题，跟本文的构建优化无关，量级也只有秒级，但排查方法本身有些参考价值。

本地 vs 远程 ​

用 hey 各跑 300 次，请求同一个小 CSS 文件：

远程访问本地直连（localhost:3000）
总耗时13.9846s0.0498s
平均响应0.0521s0.0002s
Requests/sec21.456022.09
99% 分位0.6898s0.0005s
错误53 次（DNS 解析）0

本地直连比远程快约 260 倍，说明问题出在网络传输或中间代理层，不在应用本身。这一步把 Vite dev server 排除掉了，方向锁定在平台侧。

一个假线索：DNS 报错 ​

hey 报了 53 次 DNS 错误：

dial tcp: lookup ... on <DNS 服务器>:53: cannot unmarshal DNS message

但换成 curl 跑 30 次分段计时，DNS 解析稳定在 4~5ms，一次报错都没有。原因是 hey 是 Go 写的，走纯 Go 的 DNS 解析器（netgo），它在处理多级 CNAME 跳转时有兼容问题，而这个域名的解析链特别长，要跳好几层；curl 走系统级 libc 解析器，不受影响。

所以这 53 个报错是工具自身的问题，不是真实的性能故障。

真正的现象：TTFB 尖刺 ​

30 次 curl 里，第 14 次出现明显尖刺：

#         DNS      TCP      TLS  TTFB内   总计
13        4ms      2ms     51ms     28ms     86ms
14        4ms      3ms     51ms   1302ms   1360ms   ← 尖刺
15        4ms      2ms     57ms     28ms     91ms

DNS、TCP、TLS 三段都正常，尖刺完全集中在 TTFB，也就是服务端处理时间。

放大到 200 次请求：5 次尖刺，占 2.5%，范围 250ms 到 7.2s。正常时 TTFB 只有 26~33ms。

用 s-brt 把范围锁死 ​

抓尖刺请求的响应头：

请求TTFBs-brt（后端耗时）s-rt（总耗时）DNS/TCP/TLS
#221126ms1052ms1052ms正常
#33536ms476ms476ms正常
#153340ms281ms282ms正常
#154305ms249ms249ms正常
#1827229ms7169ms7171ms正常

正常请求的 s-brt 约 21ms，尖刺时飙到 250ms 到 7.2s。

链路上延迟全部集中在代理那一层：

Client → <入口网关> → <沙盒网关> → <沙盒代理服务> → Pod(:3000)
                                  ^^^^^^^^^^^^^^^^
                                  延迟集中在这一层

几条排除：

  • s-brt == s-rt，说明沙盒网关本身没有额外延迟
  • DNS、TCP、TLS 全部正常，网络层没问题
  • localhost 直连是 sub-ms 级，Pod 里的服务本身没问题
  • 所以瓶颈是 <沙盒代理服务>

可能原因 ​

  1. 代理服务连接池或线程池饱和——多个沙箱共用同一组 proxy 实例，高峰期排队
  2. proxy 到 Pod 的转发链路偶发抖动，可能涉及容器网络，比如跨节点通信
  3. 健康检查或连接重建——长连接超时回收后重建导致首包延迟

2.5% 的尖刺发生率、最高 7.2s，对生产级服务来说偏高。已联系平台方处理。
